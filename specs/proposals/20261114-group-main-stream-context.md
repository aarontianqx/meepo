# 群主流上下文与引用图片方案（提案，2026-11-14）

状态：S1（引用图片）、S2（新会话回看摘要）和 S3（群主会话游标）已实现，规则已并入 `specs/features/interactive-session.md`。S3 的游标取最近一次聊天触发的轮次上记录的飞书创建时间（`sentAt`），不是派发时间；没有 `sentAt` 的老记录不补拉。导入的事件经 `context.append` 推给暖 worker。历史里的用户消息统一成带发言人、open_id 和 ISO UTC 时间的 `<message>`，见 `specs/features/prompt-and-context.md`。以常青文档和代码为准，本文不再维护。实现与本文的差异：缺口提示是摘要前的系统说明里的一句 `更早还有消息未列出。`（不带数量）；丢弃的是所有应用/机器人发的消息，不只是本机器人；4 张上限只作用于被引用消息的图片，触发消息自己的图片不设上限（避免回归）。起因是 Feishu 端到端验证（`20261114-feishu-e2e-findings.md`）里的一个现象：回复一条图片消息并 @ 机器人，机器人说"没有收到图片"。

## 1. 背景与问题

飞书群聊是一条连续的主流，但 Meepo 只处理 @ 了机器人的消息。当前行为（读 `decideInbound` 和 `feishu-gateway.ts` 得出）：

- 主流里没 @ 机器人的消息被直接忽略，服务端和 worker 都看不到。
- 主流里**新 @ 一次**会新开一个话题和一个话题会话（`threadRef: prewarm`），这个会话创建时是空的（`seedThreadHistory: false`）。
- 只有"回复某条消息并 @"才进群的共用主会话。回复时模型只拿到被引用消息的**文字**（最多 12000 字符），图片丢掉。
- 话题会话首次介入时，最多导入 `THREAD_SEED_LIMIT = 50` 条话题内消息，也只有文字。

两个具体后果：

1. 有人在主流里说"@bot 总结一下上面的讨论"。新会话是空的，模型什么上下文都没有。
2. 有人发一张图，再回复它并 @ bot："请描述这张图"。图片是被引用消息的，不是触发消息的，模型拿不到。

用户进一步提出的问题：A @ 了机器人，B 没 @，之后 C 又 @ 了机器人，A、B、C 是同一个会话吗？边界怎么定？C 怎么知道该拉多少才能接上？

## 2. 目标与非目标

目标：

1. 新话题会话创建时，带上主流里"这条消息之前"的最近一段，让"上面那段"有所指。
2. 触发消息和被引用消息的图片都能进模型。
3. 拉取范围有明确上限，超出时对模型可见，不静默丢弃。
4. 不把没 @ 机器人的消息持续推送给模型。

非目标：

- 不自动把 C 并入 A 的会话（见 4.1）。
- 不做主流消息的服务端滚动缓冲（见 4.5）。
- 不把话题内的回复当作主流内容推给其他会话；话题回复属于对应话题的独立会话。后期若做"援引最近信息"再单独讨论。
- 本期不让模型自己拉取更早的消息或指定图片（工具 `ChatHistory` / `LoadImage`，见第 6 节）。

## 3. 已验证的事实

以机器人身份（与 Meepo 是同一个飞书应用）调用群消息列表，对测试群的结果：

- 能读到别人发的、没 @ 机器人的消息（例如另一位成员的纯文字消息，以及一条没 @ 的图片消息）。读取主流不需要新申请权限。
- 列表里混有话题内的回复（带 `root_id`）和机器人在话题里的卡片。主流消息和话题的起点消息没有 `root_id`。用"有 `thread_id` 且不是话题起点"过滤，可以只保留主流。
- 飞书单页最多 50 条，30 条一页即可取完。

## 4. 设计

### 4.1 会话边界由用户操作决定

不自动合并会话。飞书里已有显式信号：

- 想接着 A 聊：在 A 的话题里回复。同一个话题会话，话题内本来就连续。
- 想开新话题：在主流新 @。新会话。

所以 C 不是 A 的延续，不需要"续到 A 结束的地方"。不采用"十分钟内同一个人就并入"之类的启发式：靠猜意图，猜错会把无关上下文带进会话。

### 4.2 触发消息和被引用消息的图片

被引用消息已经通过 `getMessage` 取到文字。同时返回它的图片 key，合进本轮的 `images`：

- 触发消息自己的图片和被引用消息的图片都加载。
- 一轮最多 4 张（暂定），超出的写成文字占位，不静默丢弃。
- 图片沿用现有处理：缩到 2048 以内、按消息 id 和 key 缓存、遵守当前模型的 `imageInput`（不支持时替换成说明文字）。

### 4.3 新会话的回看摘要

新话题会话创建时（以及群共用主会话尚无记录时），服务端用飞书消息列表取触发消息之前的主流消息，导入会话记录。

**范围**：触发消息之前，最近 30 条且在 2 小时内，取先到者。

为什么不用"自上次 @ 以来"：C 常常指向 A 之前或 A 本身（"总结一下今天的讨论"）。按"自 A 以来"拉，会静默漏掉 A 之前的内容，而且模型不知道漏了。固定回看的代价是 A、B 那段与 A 会话里的内容重复，但有上限，可接受。

**过滤**：

- 只保留主流：丢弃话题内的回复（有 `thread_id` 且不是话题起点）。
- 丢弃机器人自己发的消息（`/new` 通知、离线提示等），它们对模型没有信息量。
- 触发消息本身不导入（它作为本轮输入）。

**形式**：复用话题会话已有的导入路径（`appendMessage` + `externalMessageId`），不另起一套机制：

- 每条消息带发送者和时间，文字截断到 500 字符。
- 图片只写成占位（例如 `[图片]`），不加载，不进模型。
- 整体不超过 8000 字符；超出从最旧的开始舍弃，并在最前面加一行 `更早还有 N 条未列出`。
- 对"已经在话题里被机器人处理过"的消息，追加一行提示 `（已有话题会话）`，不带话题内容。

选择导入进会话记录、而不是只注入当轮：只注入当轮的话，同一会话的第二轮就忘了"上面"指什么。导入后它随会话历史一起被压缩管理，重复导入由 `externalMessageId` 去重。

### 4.4 游标：只用于同一会话的后续轮次

新会话没有"上次读到哪"，所以用 4.3 的回看窗口。游标只在**同一个会话的后续轮次**有意义，主要是群共用主会话（"回复并 @"进入的那个，长期存在）：

- 游标 = 该会话已收到的最后一条主流消息。
- 之后的消息全拉，同样受 30 条 / 2 小时 / 8000 字符的上限，超出时明示缺口。
- 游标从会话记录里最近一条带飞书消息 id 和时间的记录推出，不新增状态（单一事实来源）。

话题会话不需要游标：话题内消息已经在话题里，主流摘要只在创建时注入一次。

### 4.5 不做的

- **把所有群消息推送给模型**：成本最高，没 @ 的人的发言也会被写进会话并发给模型厂商；长连接事件丢失会造成永久缺口。
- **服务端滚动缓冲**：把群消息文本存一段时间，轮次触发时切一段。好处是不依赖飞书拉取接口的权限和延迟，但要存没被 @ 的消息，需要保留期和解绑清理，断线期间还要补。现在拉取接口权限已验证够用，先不做。
- **自动合并会话**：见 4.1。

## 5. 成本与风险

| 项       | 说明                                                                                                                                                |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 飞书调用 | 每次新会话创建多一次 `message.list`（一页，最多 30 条）。游标拉取同理。                                                                             |
| token    | 上限约 8000 字符（粗估约 3k token）每次新会话一次。图片不自动加载，一张约 1–2k token，只在触发消息或被引用时才进模型。以上是估算，不是实测。        |
| KV 缓存  | 摘要作为会话记录追加，不改 system prompt，缓存前缀不受影响。                                                                                        |
| 遗漏     | 超出上限时在摘要最前面写明缺口，模型知道有更早的内容。数据源是飞书本身，不依赖事件，服务停机期间的消息不会丢。撤回、编辑后取到的是当前状态。        |
| 隐私     | 摘要包含没 @ 机器人的成员的发言，写入会话记录（永久保留）并发给模型厂商。与"绑定群即信任群内全体成员"一致，但数据流向有变化，实现时需写入常青文档。 |
| 提示注入 | 群里其他人的文字进入模型上下文，与话题历史导入同一信任边界。用与引用消息一致的标签包裹，并标明是参考资料而非指令。                                  |
| 重复     | 固定回看会让 A、B 与 A 会话重复，上限内可接受。                                                                                                     |

## 6. 实现切片

1. **S1 引用图片**：`getMessage` 返回图片 key；网关把触发消息和被引用消息的图片合并，最多 4 张；超出的写占位。
2. **S2 新会话回看摘要**：话题会话创建时调用主流回看，过滤、截断、缺口提示、话题提示，经现有导入路径写入。
3. **S3 游标**：群共用主会话的后续轮次按游标拉取。

测试要点：过滤规则（话题回复被丢、话题起点保留、机器人消息被丢）、三类上限（条数、时间、字符）及缺口提示、`externalMessageId` 去重、图片上限与不支持图片时的占位、游标从会话记录推出。

暂不做、留待后续：`ChatHistory` 和 `LoadImage` 工具；摘要里图片的按需加载；"援引最近信息"（跨话题引用）。

## 7. 实现时需要核对

- 机器人自己的回复是否在会话记录里记了飞书消息 id；游标取"最近一条带飞书消息 id 和时间的记录"依赖这一点，缺失时改用最近一条触发消息的飞书创建时间。
- 过滤规则用的字段（`thread_id`、`root_id`）在不同消息类型上的实际取值，用测试固定，不凭记忆。
- 图片上限 4 张、条数 30、时间 2 小时、字符 8000 都是暂定值，以实测的成本和体验为准。
- `message.list` 的限流；一次新会话一页，应远低于限额，但群很活跃时并发创建多个会话需确认。
